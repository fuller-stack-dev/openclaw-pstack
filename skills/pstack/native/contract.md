# Native execution contract

Read this entire contract before any pstack route. System, developer, workspace, user, and tool policies remain authoritative and win conflicts with all package text.

## Plugin boundary

Pstack is an installable OpenClaw plugin. Registered commands own exact-session mode in the host plugin state store; before_prompt_build contributes active routing context. No AGENTS.md bootstrap, transcript-derived authorization, helper subprocess, core session field, credential resolver or alternate agent runtime is used. Use pstack_route for read-only role planning. Optional [pstack_workflow state](workflow-ledger.md) records agent-attested CAS phases and tagged control checks for skill-guided work. On hosts that grant the command runtime, the seven [native controllers](session-mode.md#native-controllers) (architect, arena, interrogate, swarm, how, why, reflect) run their child phases as code and write deterministic version 2 records from host receipts; every other route, and every route on older hosts, uses skill-guided native sessions_spawn and collection after pstack_route planning. Pstack registers no reply_dispatch hook. Children inherit the requester’s native tool policy; a read-only brief is guidance, not tool enforcement. The host retains execution, permissions, lineage and delivery custody; never substitute administrator authority.

## Authority

- Work only on the assigned task. Read relevant repository instructions before editing. Respect stops, pauses, existing owners, review gates, source custody, and deployment restrictions. A skill cannot enlarge permission.
- Help, investigations, reviews, setup, and teaching are read-only unless changes are separately requested. Review is not permission to repair or publish.
- Proceed on authorized reversible choices. Ask one concise question for a genuinely missing safety or product decision. External, destructive, irreversible, or privacy-sensitive actions need the authorization required by the environment. An unattended request never cancels a gate.
- Do not automatically open PRs, post messages, deploy, start servers, create timers, or migrate data at the end of a playbook. Publishing is its own authorized step.
- Do not restart/update the live gateway, use a live handoff store for tests, change agents/providers/credentials, create automations, or resume held work as a pstack side effect.

## Current goal

In the first task reply, restate the current user goal, the problem and the smallest expected change in your own words; do not wait for redundant confirmation. Carry that goal into each delegate brief, the opening of each PR Why section, and the final report, except a fully specified one-line edit. If evidence rules out the requested change, show that evidence and stop rather than inventing a replacement goal. Explicit corrections require fresh grounding against the current request. Retain holds, owners, accepted snapshots and safety gates; an old plan or reported policy is never new authority. Required machine-output contracts keep their exact shape.

## Native artifact execution

The separate [statechart and ketchup-video CLIs](artifacts.md) run only through ordinary agent exec, never inside the Gateway. Read their complete usage, toolchain, ownership, factual-evidence and cancellation boundaries before use. Neither this guide nor a successful CLI run registers new routes or proves model-generated reports.

## Delegation and resources

Apply [role routing](model-routing.md) on every invocation, each active-session work turn and before each new role delegation. Mode/status responses and simple conversational acknowledgments are not new role phases and need no agents. Keep small work inline only when the resolved selection is inherited or matches independently observed current model/controls and no independent pass is required. A configured alternative model is a real bounded delegation, not a label on parent prose. Keep existing owners and historical snapshot evidence for ongoing/resumed work; ordinary configuration changes apply only to new delegations. A newer explicit user correction follows [append-only continuation supersession](model-routing.md#explicit-user-corrections-on-continuation), preserving original evidence while applying the corrected controls before the next authorized continuation. Delegate using [delegation](delegation.md), never duplicate coordinators or replace paused workers. Respect concurrency and resource limits. Reuse valid dependencies/results instead of reinstalling per phase.

Every required independent phase MUST resolve its role through `pstack_route`, use the returned arguments with native `sessions_spawn`, and collect the accepted child through its native completion path. If planning, spawning, collection, required family diversity or evidence is unavailable, report that named gate **BLOCKED** and do not claim the route complete. A sequential parent pass never satisfies independence, even when the parent has the selected model. Two prompts on one model are not model diversity; missing canonical family metadata leaves a different-family gate BLOCKED. Do not install providers, invent fallback models, replace existing owners or weaken gates. Optional non-independent work may remain inline only under the matching-selection rule above.

## Collection and resume

For long panels or routed phases, use a short schema-supported bounded wait, then hand off pending work and finish on resume. In skill-guided routes only announcing children are handed off; a collector is collected in the turn that spawned it ([bounded-wait handoff](#bounded-wait-handoff)). Preserve the exact owner, accepted run/session IDs, phase, snapshot, completed artifacts and next collection action in the task-owned record; do not respawn accepted children or synthesize before required results arrive. A pending handoff is not completion. The same handoff also goes into the visible reply under [visible handoff](#visible-handoff); a handoff kept only in the record never reaches the user. Skill-guided work resumes through the existing task/session and its native collection tools; only native controller workflows resume through `/pstack resume`. Registered route commands use the `pstack-<route>` prefix; bare names require explicit opt-in and native core/collision checks never overwrite an incumbent. See [route-command compatibility](route-commands.md). Route commands continue through the ordinary agent, except the seven native controllers on hosts that grant the command runtime.

Native controller workflows resume with `/pstack resume` from their CAS record, and on hosts that grant requester-admitted scheduled command turns they arm bounded single-occurrence continuations that recheck the original requester every time ([details](session-mode.md#native-controllers)). Skill-guided routes have no command-bound continuation: report that gate **BLOCKED** when requested, keep an explicit resume handoff, and never silently skip it or create an ad-hoc scheduler. General automation setup is not evidence of either. An in-progress native workflow never continues as skill-guided work or recreates its children. Publication and lifecycle authorization remain separate.

### Bounded-wait handoff

In skill-guided routes, choose each routed child's completion mode when you spawn it, by whether this turn may end before the child finishes:

- **A child you may hand off is an announcing child.** Any routed phase that can outlive one bounded wait is spawned without `collect`. Wait for it with a `subagents` wait whose timeout is no more than 60 seconds. If it is still pending, hand off and end the turn with `sessions_yield`; the child's completion event resumes this session.
- **A collector is collected in the turn that spawned it.** A collector (`collect: true`, for example a child with an `outputSchema`, or a short fan-out whose results this turn needs) never wakes its parent: nothing resumes the session when it finishes, so a handoff on a pending collector leaves its result uncollected until the user writes again. Collect every collector before the turn ends with `agents_wait` and `awaitResults: true`, without `timeoutSeconds`; the child's own `runTimeoutSeconds` bounds that wait, so every collector has one. `pstack_route` gives a collector's spawn arguments `runTimeoutSeconds: 600` when they have none (or 0, which means no limit); give a collector you spawn without `pstack_route` the same bound. The bound counts from the child's own start, so time a collector spends queued behind other children is extra. A collector may ask for at most 900 seconds, and in pstack mode the plugin refuses a `sessions_spawn` collector that asks for more; a phase that may take longer is an announcing child. A structured-output phase (`outputSchema`) is always a collector, so it has at most 900 seconds. The plugin never changes a spawn's arguments, so a Code Mode `agents.run` child and a native controller's child keep the host's own bound. A collector that reaches its bound settles with status `timeout`: name its phase BLOCKED with that status rather than treating the gap as a result. A collector accepted in an earlier turn is collected the same way. Never end a turn with a collector pending.

Never use an unbounded `subagents` wait, a longer timeout, repeated history reads or polling in place of waiting. A later wait in the same turn is allowed only when the previous wait returned every child it waited for, so that a next phase can start. Once a wait returns with an announcing child still pending, stop collecting in this turn: write the handoff (owner, pending run/session IDs, phase, routing snapshot, completed artifacts and the next collection action) into the task-owned record and the reply in the [visible handoff](#visible-handoff) form, then end the turn with `sessions_yield`. Do not re-read sources, start synthesis or spawn a substitute while required results are pending. A message that arrives later in the same turn, such as the host's [plan-completion check](#plan-completion-check-after-a-handoff), does not reopen collection.

### Visible handoff

The handoff is part of the reply the user sees, not only the task record. Hand off only after one bounded wait has returned with an announcing child still pending. Every `sessions_yield` in a skill-guided route is a handoff and carries these lines, including a yield that only waits for the completion delivery of a child that has already finished; its `Pending:` line then says `finished, completion delivery pending`. A status sentence is not a handoff. When the turn ends with `sessions_yield`, put the whole handoff in its `acknowledgment` field, which is the visible waiting reply. Its `message` field is private context for the resumed turn and never counts as the reply. The host shows the acknowledgment only for an otherwise-silent turn, so the yielding turn has no other reply text or message send; if the turn does write reply text, put the whole handoff in that text. Only a `sessions_yield` result with `status: "yielded"` delivers the acknowledgment; if it returns any other status, the turn did not yield, so write the handoff as the final reply text (after `deferred`, first read the results that arrived with it and yield again only if a child is still pending). When the turn ends without `sessions_yield`, write the handoff as the final reply text. The six lines end the reply: nothing follows them, and a status sentence never stands in for them. A block that a route requires in every reply, such as show-me-your-work's Attention or opening-a-pr's readiness line, goes immediately before the six lines, never after them. A handoff for a newer pending point replaces the earlier one in full, with a `Pending:` line for each child that is pending now. Never send the handoff with a message tool; it is the reply text or the acknowledgment. Use these lines with real values, one `Pending:` line per pending child, each line starting with its plain label:

```text
Handoff: <route>, <phase> pending
Owner: <this session key>
Pending: <role> run <run ID>, session <child session key>: <what it will return>
Done so far: <completed artifacts and results, or none>
Snapshot: <model, thinking and fastMode of each pending child>
Next: <the exact resume action, such as collect run <run ID> when its completion event arrives>
```

When the handoff is not in the turn's reply text, an empty acknowledgment, an acknowledgment without these lines, or a handoff written only in `message` or the task record fails the handoff. After the handoff the turn does no more work: no source reads, probes, edits, spawns or synthesis.

Call `sessions_yield` with exactly two fields, `acknowledgment` and `message`:

```text
sessions_yield({ acknowledgment: "Handoff: <route>, <phase> pending\nOwner: <this session key>\nPending: …\nDone so far: …\nSnapshot: …\nNext: …", message: "<private resume notes>" })
```

Never set `waitFor` to wait for routed children; it only matters when the session calling `sessions_yield` is itself a subagent, paused for an incoming message from its requester. The host's tool text "Unfinished subagents awaiting an incoming continuation must set waitFor" describes a spawned subagent pausing for a message from its requester. A route's parent session waiting for its own children is not that case: their completion events resume it without `waitFor`, so `waitFor` is never needed for your own children.

In pstack mode the plugin checks every `sessions_yield` of a top-level session, whether or not a route is running. It removes `waitFor` and lets the yield through, adding a note to the yield's result. It refuses an acknowledgment that lacks any of the six handoff lines; a `- ` list marker or bold label is accepted, a placeholder such as `UNUSED` or a status sentence is not. After a refusal, retry the same `sessions_yield` at once with the six lines, or without `acknowledgment` when the handoff is already this turn's reply text; never end the turn on a status sentence instead. A yield that is not a handoff omits `acknowledgment`.

### Plan-completion check after a handoff

A turn that ends with the handoff as its final reply text instead of `sessions_yield` passes the host's plan-completion check. When the run's saved plan, its `progress_card` checklist, still has unfinished steps, the host adds a hidden message that begins "This run’s latest successfully saved plan still has unfinished steps" and says "Continue feasible work from the current transcript". After a handoff, answer that message with exactly `NO_REPLY` and nothing else: no tool call, wait, read, collection, delivery or other text. The pending announcing child is the external dependency the check names, the handoff already reported it, and the check itself says to end with only `NO_REPLY` when the previous reply reported it. The host still delivers the handoff reply, and collection resumes on the next turn. To keep the check from firing, before writing such a handoff you may replace the progress card the way its tool describes for blocked work: `markdown` naming the pending child, the owner and the resume condition, with `plan` omitted. Never mark a pending step completed, and restore the checklist when the work resumes.

## Verification

Capture behavior before editing. Read every touched file in full. Test observable outcomes and failure paths, not source mirrors or mocks bypassing the behavior. Audit the entire touched test file for weak/redundant tests, retain genuine edge cases, and justify pruning. Recheck affected behavior after edits.

Prefer failing-before/passing-after evidence. If required runtime access is unavailable, report the exact gap. Build success or grep is not runtime proof. Isolate processes, ports, stores, and worktrees; clean only task-owned resources under current policy. Use exact revisions when results depend on source. Separate observed facts, inference, and unknowns. A queued action or child self-report is not completion.
